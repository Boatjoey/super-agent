# 终端界面设计（UI）

本文件定义界面如何呈现。操作流程和反馈时机由 [UX 设计](ux.md)定义，精确终端行为由[终端规范](../spec/terminal.md)规定，界面所需数据由[应用接口规范](../spec/application-interface.md)提供。

## 对标目标与范围

体验参照见[产品定义](product.md#前端对标目标)。本项目在终端中提供清楚的对话层次、持续可编辑的输入区、工具活动、审批和状态提示。截图中的 IDE 面板不作为布局基线。

核对日期：2026-10-27。[Codex 官方 CLI 页面](https://learn.chatgpt.com/docs/codex/cli)展示了模型、项目目录、输入和上下文提示，并说明终端中的代码工作循环。[官方命令参考](https://learn.chatgpt.com/docs/developer-commands?surface=cli)说明了运行中引导、排队输入和终端模式选择。以下是本项目据此提出的设计，不是对 Codex 每个版本布局的逐像素复刻。

界面采用“对话内容、当前活动、输入编辑、状态提示”的结构。已提交内容进入终端滚动历史，当前活动和输入区在最新内容之后保持可用，输入区下方展示状态与上下文提示。运行中输入仍可编辑；新输出不能覆盖草稿，审批期间也能辨认原任务和当前操作。

本阶段采用保留终端滚动历史的交互形态，当前输入和状态组成可更新的交互区，不要求全屏备用屏幕。项目仍只有一个终端入口，沿用自己的 Agent 后端与应用接口。具体键位、刷新、换行和缩放由终端规范细化；待完成工作及其推进情况由 [gap](../gap.md)与 [flow](../flow.md)维护。

## 信息层次

| 信息 | 呈现方式 | 目的 |
|---|---|---|
| 工作上下文 | 展示项目、模型、权限模式和会话标识；模型支持时显示推理强度 | 让用户知道正在什么环境里工作 |
| 用户输入 | 使用输入提示符作为清楚的起点，与回复留出间距 | 能在长历史中找到用户意图 |
| 助手回复 | 正文使用默认前景色，保留段落、列表和代码块层次 | 保证长文本可读 |
| 推理内容 | 使用次要样式，弱于正式回复 | 避免与结果正文混淆 |
| 工具活动 | 单独标明操作名称、执行状态和必要结果 | 让用户识别外部操作 |
| 审批请求 | 独立成块，展示操作、范围、原因及决策选项 | 在执行前提供足够判断信息 |
| 进展和结束状态 | 以简短文字标识活动变化、完成、取消或失败 | 不依赖颜色猜测状态 |
| 后续输入 | 展示其“中途引导”或“排队”意图及接纳状态 | 避免与当前执行内容混淆 |

内容区域承载已提交历史与当前活动，输入编辑区承载草稿，状态提示位于输入区下方。交互区刷新时不重复写入已提交历史；具体渲染规则以终端 Spec 为准。

## 空闲与开始工作

```text
Super Agent   项目：当前项目

  对话历史和已完成的工具活动

────────────────────────────────────────
❯ 描述任务或输入命令
────────────────────────────────────────
模型：当前模型 · 权限：当前模式 · 空闲
```

输入编辑区和状态提示保持容易找到；工作上下文不在每条助手消息中重复。状态信息只展示应用接口能够确认的事实，缺少能力或数据时不编造推理强度、限额或剩余上下文比例。

## 执行中的界面

```text
❯ 修复失败的测试

● 我会先定位失败原因。

  工具 · 读取相关文件 · 已完成
  结果 · 已取得文件内容

  工具 · 运行测试 · 执行中

────────────────────────────────────────
❯ 先不要改动公共接口
────────────────────────────────────────
执行中 · 输入可继续编辑 · 提交方式见操作提示
```

助手、工具和状态使用不同的文字标识与缩进。已提交历史与实时活动层次分明，正式结果不混入未经结算的工具输出。输入草稿与输出流互不覆盖，用户能够继续编辑和选择提交意图。

## 审批界面

```text
需要审批 · 执行操作

操作：请求执行的具体操作
范围：涉及的目录或文件
原因：需要本次审批的原因

1. 允许一次
2. 始终允许
3. 拒绝

请选择：
```

具体操作信息应足够用户判断影响范围。决策后，该审批条目应体现已作出的选择，避免仍显示为等待中的请求。缺失的信息不编造显示。

## 后续输入的呈现

```text
中途引导 · 先不要改动公共接口
状态 · 等待下一步骤接纳

排队输入 · 修复后再整理说明文档
状态 · 等待下一轮
```

两种输入的标签和反馈应可区分；输入归属由[核心概念](concepts.md#输入归属)定义。已提交与已接纳是不同状态，界面应依据应用反馈呈现。

## 完成、取消与失败

```text
● 已修复问题，并完成相应验证。
本轮已完成

────────────────────────────────────────
❯ 继续当前会话
────────────────────────────────────────
模型：当前模型 · 权限：当前模式 · 空闲
```

取消时使用明确的“本轮已取消”，有已发生的操作时保留其记录。失败时显示错误说明与必要上下文，不显示成功样式。是否可以继续输入由应用状态决定。

## 视觉规则

界面采用终端默认前景色，以及 ANSI 青色、绿色、红色和品红色；不构造 RGB、十六进制或索引颜色，也不使用蓝色或黄色前景色。语法高亮拥有独立主题。

- 默认前景色承载主要正文。
- 青色用于可操作提示和结构标识。
- 品红色用于区分 Agent 活动与辅助状态。
- 绿色表示成功，红色表示错误；同时保留明确文字。
- 推理和补充信息使用弱化样式，不降低正式结果的可读性。

颜色关闭或终端配色改变时，结构、文字标识和状态仍应可理解。长路径、长结果和窄窗口应保持内容顺序清楚，不因截断隐藏决定操作风险所必需的信息。

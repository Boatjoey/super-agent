# 质量目标与约束

本文件规定实现产品功能时必须保持的性质。产品范围见[产品定义](product.md)，业务职责见[软件架构](software-architecture.md)。具体状态、限额和错误响应由对应 Spec 细化。

## 授权与工作范围

用户必须能够控制 Agent 的操作范围。模型提出操作建议后，系统应先按权限策略处理，再交给外部能力执行。

应用层授权与操作系统隔离分别承担权限决策和执行约束的责任。命令分类不能代替执行隔离；启用的严格隔离条件不满足时，不得悄悄降级后继续执行。

文件访问权限与指令、扩展及配置的信任范围必须分离，获得目录访问权限不自动获得改变 Agent 行为的权限。

具体规则见[配置规范](../spec/config.md#权限)、[工具规范](../spec/tools.md#沙箱)及[会话规范](../spec/session.md#初始上下文)。

## 可取消与状态一致性

用户应能够停止当前执行，停止后的会话应保持可理解、可继续的状态。

取消、状态决策生效和待执行工作之间的一致性由[软件架构中的执行约束](software-architecture.md#执行约束)规定。取消不能保证撤回已经发生的外部副作用，历史必须反映实际已发生的工作。

可验证的状态条件与异常路径见[状态机规范](../spec/machine.md)和[运行时规范](../spec/runtime.md)。

## 可恢复与持久化一致性

保存的会话应足以重建约定范围内的历史和工作环境。恢复前必须重新验证当前环境，不能因为过去曾经授权就信任已经改变的路径。

涉及历史替换、重置和撤销时，应保证失败不会被报告为成功，不以丢失原历史的方式掩盖恢复失败。

已有持久化数据应保持可读取；确需改变保存格式时，必须明确兼容与迁移语义。具体顺序和格式要求见[会话规范](../spec/session.md)及[磁盘格式稳定性](../spec/session.md#磁盘格式稳定性)。

## 可观察与可解释

用户应能够观察响应、工具活动、审批、取消与错误，区分已有成果和未完成工作。错误信息应帮助判断工作停在哪里，不得把失败或未完成状态呈现为成功。

流式展示和历史记录应保持一致，具体通知、输出及记录规则见[终端规范](../spec/terminal.md)和[会话规范](../spec/session.md)。

## 可替换与可维护

模型、工具、存储与工作环境的可替换边界由[软件架构中的依赖方向](software-architecture.md#依赖方向)规定。外部能力替换后，业务语义必须保持一致。

规范应能够作为独立于当前实现的验收依据。跨多个部分的变更应沿既定职责边界展开，避免将相同业务规则分散到多个位置。

## 资源与响应

外部调用、工具输出、文件读取和附件处理应有与用途匹配的时间或大小边界，取消与失败后应释放本次执行占用的资源。

具体限额以[工具规范](../spec/tools.md)、[配置规范](../spec/config.md)和[会话规范](../spec/session.md#附件)为准。当前没有统一的延迟或吞吐量目标；后续提出性能要求时，应给出场景、测量方法和验收阈值，不预设未经验证的数字。

## 验证方式

每项质量要求应在相应 Spec 中体现为可验证的正常、失败或边界行为。自动检查与人工验收的分工由[开发指南](../development.md#验收)规定；通过某一项测试不能替代对全部约束的验证。

# 使用体验设计（UX）

本文件定义用户怎样完成任务、怎样理解反馈及从中断中继续。界面呈现见 [UI 设计](ui.md)，业务概念见[核心概念](concepts.md)，精确行为见[终端规范](../spec/terminal.md)与[应用接口规范](../spec/application-interface.md)。

## 对标目标

体验参照选择见[产品定义](product.md#前端对标目标)，界面形态见 [UI 设计](ui.md#对标目标与范围)。

## 用户体验目标

用户能够明确回答：正在什么环境中工作、Agent 当前在做什么、是否需要自己决定、输入是否已被接纳，以及本次工作产生了什么结果。

运行中应能够观察和干预；失败后应能够区分已完成的外部操作与尚未完成的工作。界面只呈现应用服务提供的事实，不根据等待时间或局部输出推测执行成功。

## 开始任务

1. 用户确认当前项目、模型与权限模式。
2. 输入任务，可附带工作区附件或通过命令准备上下文。
3. 界面明确反馈提交状态，应用接受后进入本轮工作。
4. 如果应用拒绝提交，说明原因，不将未接纳输入显示为已开始的工作。

## 观察执行

用户不需要持续操作即可看到新增回复、工具活动、审批请求和错误；执行期间仍能编辑后续输入。长时间执行时，仍能识别系统是在处理、等待用户决定，还是已经结束。

界面中的推理和工具活动帮助用户理解过程；最终结果应说明本轮实际完成的工作。显示了工具输出或用量信息，不表示该轮已经成功结束。

## 作出审批决定

用户先查看具体操作、影响范围和审批原因，再选择允许一次、始终允许或拒绝。

选择后应知道决定已经提交还是已经生效。相同请求不重复提交，已经失效的请求不能作用于另一项操作。拒绝是否导致后续调整由业务规则决定，界面不自行结束整个轮次。

## 执行中调整方向

用户可以表达中途引导或排队两种意图，其归属以[核心概念](concepts.md#输入归属)为准。

- 提交后保留可辨识的输入反馈，避免用户因没有看到效果而重复提交。
- 应用尚未接纳时，显示等待位置；接纳后依据确认反馈更新。
- 选择中途引导不应让用户误以为正在执行的工具会被立即打断。
- 排队输入的等待不应被误解为当前轮次没有响应。

运行中使用不同提交动作表达中途引导与排队，具体键位及其上下文优先级由[终端规范](../spec/terminal.md#运行期间的输入)唯一规定。草稿编辑不等于提交，也不因新输出到达而自动提交。

## 取消与结束

取消操作表达停止当前工作的意图。应用确认停止前，界面不能直接显示取消已完成；停止后保留已经发生的操作及已产生内容。

正常完成、取消和失败应可区分。空闲时退出的操作不得被误解为取消另一轮任务，具体按键语义由终端规范定义。

## 会话与工作环境切换

恢复、分支、重置、压缩和撤销应反馈操作结果，并在成功后呈现应用返回的会话和上下文。切换失败时应说明当前仍在使用的环境，不能仅凭用户发出请求就把新环境显示为已经生效。

功能所能恢复或撤销的范围由[会话规范](../spec/session.md)定义，不在界面承诺额外恢复能力。

## 错误与恢复

错误应能帮助用户区分输入未被接纳、外部操作失败和本轮工作失败。能够继续处理时不应将界面永久锁住；需要用户行动时说明下一步。

恢复视图依据应用提供的快照和通知，不能通过重新提交任务来重建界面，以免重复发生外部操作。

## Web 任务流程

### 进入、加载与恢复

1. 页面先提供可识别的导航、对话和输入骨架，再分别读取配置、会话列表和快照；任一请求失败不影响其他已成功区域呈现。
2. 快照到达前不能将列表或对话误报为空。空数据只有在成功响应确认后才显示对应空状态。
3. 事件流连接状态始终可见。断开后自动重连，恢复时消费新快照重建界面，不重新提交任务、不重复外部操作。
4. 初次读取失败时在对应区域给出原因和重试入口；已经存在的历史不因后续配置或列表刷新失败而清空。

### 开始与干预任务

- 用户从空状态示例或输入框开始任务。提交后立即清空草稿并等待受理；失败时恢复草稿，成功时以事件流报告实际状态。
- 运行中可继续编辑。发送动作表达中途引导，排队动作表达后续轮次，两者使用不同回执文案；未受理时保留或恢复草稿。
- 停止请求只表达取消意图，按钮进入受理中，直到应用报告轮次结束后才恢复空闲状态。
- 审批期间展示足够上下文，同一请求的决策只提交一次；迟到或重复回应用错误反馈说明，不能切换为已生效样式。

### 会话、配置与轻量反馈

- 恢复会话时标记目标项为加载中并避免重复点击；成功后以推送快照为准，失败时保留当前环境和错误说明。
- 新会话、权限切换、记忆开关和模型配置在请求期间显示对应进度，只有成功响应后才采用新值。
- 短暂回执用于已受理、已保存等轻量结果；错误同时在相关区域保留可重试入口，不能依赖几秒后消失的消息完成恢复。
- 设置对话框支持取消、遮罩和 Escape 关闭，并管理焦点；未保存的密钥不因界面重绘被写入日志或消息。

### 移动端与键盘

移动抽屉让用户能完成新会话、恢复会话和查看工作上下文，打开时不误触背景。选择会话后关闭抽屉并显示恢复进度。屏幕键盘弹起时输入框和主要动作仍可到达，长内容只在各自滚动容器内移动。

键盘用户可以到达导航、消息折叠、审批、输入和设置。Escape 的优先级为设置对话框、移动抽屉、运行中取消；组合输入期间不提交。减少动态效果偏好不影响状态内容和操作反馈。

## 验收视角

- 用户能否找到输入、审批、取消和继续工作的入口？
- 能否区分已提交、已接纳、等待、执行中和结束？
- 能否在纯文本或颜色关闭时理解关键信息？
- 新增内容是否及时可见，正式回复是否与流式内容一致？
- 发生失败或取消后，是否清楚哪些工作已经发生、哪些尚未完成？

这些体验目标由终端和应用接口 Spec 转为具体可验证条件；Web 的呈现与流程按本文件和 [UI 设计](ui.md#web-信息架构)验收。当前能力与目标之间的差距统一记录在 [Gap](../gap.md)。
